### Real entropy rather than deterministic SDK filler
The pinned SDK's actual XeCryptRandom implementation writes the same byte 0xFD throughout every request. This is a concrete functional defect for original key-generation and retry code, particularly the observed deferred XAM fallback. It is not yet proven that the stalled 818A6DA8 call consumes this export. The corrected hosted implementation fills the exact checked guest extent with OS cryptographic randomness: BCryptGenRandom on Windows, getrandom on Linux (handles interrupted/partial reads), arc4random_buf on macOS. A zero-length request is a no-op. An invalid nonzero extent or entropy-provider failure terminates rather than emitting fabricated random data. No entropy bytes, private keys, account data or credential values are logged; opt-in Guide diagnostics count successful requests only. Native tests check differing successive outputs, variation, guard words, zero-length calls, and a request crossing the 256 KiB chunk boundary. No original key validation, key vault or sign-in flag is overridden. Guide initialization must be re-tested end to end.
