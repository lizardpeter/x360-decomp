# Original Guide activation evidence

Integrated run 46028436241: the hosted pad emitted 0x0400 and returned to zero, but none of the captured Guide frames differed from the baseline. No original profile UI entry was observed. The input bridge's successful read alone is not proof of Guide activation.

The original XAM imports DrvSetSysReqCallback at 0x81A72FF4 (ordinal 0x020C). The existing direct-call census identifies four original callers: 816F0368, 816F0410, 816F0AE0 and 816F0DF0. XamInputSendXenonButtonPress (816F2E60), XamShowGuideUI (816C3580) and XamIsGuideDisabled (816E16F0) are independently joined to the original export table. The audit reconstructs the actual registration arguments and bounded candidate callback bodies, reads the input and HUD call sites, and supplies precise original trace points. No private account data or executable payload is emitted. Do not assume a callback ABI or forge a Guide launch.

## First original callback proof

Run 46032021939 succeeded. Five original registration calls were found, four setting the same callback 0x816F09E8 and one clearing it. The original callback forwards its three registers r3/r4/r5 to the common request handler 0x816F06E8 as r4/r5/r6, loading its own object pointer from guest global 0x81AAC260. That handler checks 0x81AAC264 and other original state before posting through 0x816F0368 to KeSetEvent. It also calls original 0x816D8AA8 to resolve the device and user. The worker at 0x816F0AE0 tests Guide-disabled state, permissions and original request fields. Constructor 0x816F0E70 allocates a 36-byte object, publishes 0x81AAC260 and calls 0x816F0DF0; only after that worker is successfully registered does 0x816F0E54 register the original system-request callback. The previous live log has no DrvSetSysReqCallback call, so merely adding the host callback API is insufficient if the original worker never starts. Next trace the original initializer's table and its status, without forcing it to run.

## Second original lifecycle proof

Run 46032405471 succeeded after correcting the evidence scanner's PDATA tuple unpack. The original public XamInputSendXenonButtonPress tail invokes 0x816F0400, which explicitly sets r5/r6 to zero and posts request type zero to the same original worker. The independent original input message handler 0x816F3C48 passes a real device context from 0x816D8A58 and zero subdevice/type to 0x816F06E8 at 0x816F3E14; the driver callback 0x816F09E8 forwards exactly that tuple. The original device lookup at 0x816D8AA8 scans four guest user groups using the low byte of its subdevice argument and compares the exact opaque device context. Therefore a hosted button event must carry the bound context, subdevice zero and request zero; passing a guest user index as the context would be wrong. The initialization chain contains the original UI initializer 0x816CE8B0 -> 0x816F0F28 -> 0x816F0E70. Six original independently bounded wrappers are explicitly hinted, including callback/worker and public Guide exports. The live trace will identify which stage runs or fails.

## Third lifecycle proof and opt-in hardware experiment

Run 46033382691 resolves the original UI callback 816CE8B0 as a nonadjacent constant loaded into r5 at 816CEC68 and submitted at 816CEC70 by 816CEBD8. Original deferred startup 81696558 calls that registrar at 81696724 only when XboxHardwareInfo (kernel ordinal 0156, original XAM slot 815F0480) has bit 0x200 set. The preceding graphics initializer 816C9EA0 independently tests that same bit at 816C9EB8. The pinned SDK initializes its hosted flags to 0x20; earlier live startup reached the deferred worker but not the UI registrar. No official name or physical hardware semantics for 0x200 is asserted. X360_METRO_GUIDE_UI=1 is a deliberately isolated diagnostic changing only the verified hosted kernel variable from 0x20 to 0x220 before original XAM attach. Existing retail checks, initialization, and dispatch remain unmodified. Normal boot stays unchanged; the integrated Guide probe opts in. The capture records actual callback delivery, original callback execution, worker entry and HUD traces separately from screenshot changes, which require visual inspection. No account data is mounted.

## Graphics registration and resource-only skin

Run 46034183440 recovered 54 graphics-related XAM calls and the original UI loader path at 816CEA04, `\\SystemRoot\\huduiskin.xex`. The pinned SDK has stub VdRegisterXamGraphicsNotification and VdRegisterGraphicsNotification and a no-op VdCallGraphicsNotificationRoutines. Separately, the original skin is a resource-only XEX at 90F90000 (233472 bytes), with no imports or executable PE, containing XUIZ `skin` and `xam` archives. Both pinned SDK decode and LoadContinue previously required a PE. The narrow resource-only path requires the exact recovered layout, no executable page or entry point, and existing compressed-block verification, then uses ordinary guest image ownership, protection and module registration. It does not fabricate an executable module or claim Guide activation. Live resource mapping and graphics callback dispatch still need validation.
