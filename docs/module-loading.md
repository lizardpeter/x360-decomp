# Native module loading and ordinal resolution

The native loader accepts an independently verified decoded XEX image and its module-qualified manifest. It checks image sizes, mapped section extents, original import words, duplicate addresses and ordinals, executable entry points and address collisions. A transaction maps section data with original write permissions and gaps/tails as read-only, then publishes the module registry. No partial mapping is retained on a failed batch. This is a bounded initial address space, not a full Xbox MMU or native XEX decompressor.

The registry resolves original imports by exact provider library and ordinal. A value slot can resolve to an executable or data address; a thunk must resolve to executable code. An address match is not an implemented function, and a missing provider or ordinal stays unresolved. The original dashboard and XAM contain 2,534 import slots: 1,044 dashboard XAM slots, 1,490 kernel slots across both modules. XAM has 1,606 populated exports, 1,604 in executable sections and two in data sections. Of 522 dashboard XAM ordinals, ordinal 987 has both a value and thunk slot targeting 0x81A87F20 in .data. The registry retains the value address and flags the thunk as non-executable rather than pretending it is callable. The kernel imports cover 519 distinct ordinals across both images; all remain unresolved because no kernel provider is loaded.

The audit verifies the original image digests, exact section tables, imported slot records and XAM exports before constructing the native maps and exercising every slot. No import patch, generated PPC execution, thread initialization, original entrypoint execution, or full dashboard boot is performed. The loader is independent of the future execution backend and can support authored or statically recompiled providers.
