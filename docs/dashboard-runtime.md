# Local dashboard launch resource tree

The staging tool verifies the pinned PIRS and shared resource sources and checks the entire 31-member census before writing the explicit 14-file base runtime tree (dashboard, boot animation, ten selected system modules, one original font resource and shared XUI archive). This is an input layout for a hosted diagnostic session, not a claim of the original flash filesystem layout or a bootable dashboard. It checks the dashboard/XAM hashes against the AOT inputs, never overwrites different files, rejects unsafe destinations, and produces a digest-only receipt. Optional full font complements must be supplied locally and match the exact size/hash pins in target.toml; missing complements are explicitly reported. No patch files are treated as full resources, no encrypted manufacturing module or updater is launched, and no original files or fonts are committed or published. The native validation workflow exercises the base staging tree from verified inputs; it does not execute the guest.

For a local build, after acquiring the pinned pirs and shared_resources objects:

```sh
python tools/stage_dashboard_runtime.py --font-dir /path/to/your/local/originals --require-fonts
```

The default destination is the ignored AOT dashboard input directory. The SDK and our eventual hosted loader must still mount and register the system modules, configure the original UI services and render the dashboard. A receipt records guest_boot_verified=false.

## Counted-name object ABI and device completion correction

The verified original-image artifact from run 45952022377 contains 17 XAM function groups with ObReferenceObjectByName and subsequent device control/dereference. At 8167AB34 and 8167ABC4, RtlInitAnsiString initializes a stack descriptor at r1+88; at 8167AB4C and 8167ABDC the descriptor is passed as r3 to ObReferenceObjectByName, with output at r1+80. The original uses a signed status check before consuming that output. The pinned SDK accepts MappedString instead of the original counted descriptor. The corrected entry validates descriptor, bytes and output before acquisition; successful lookups return owned references; missing names return an error without overwriting the caller's output. The bodyless reference path also no longer returns a null body as successful. IoSynchronousDeviceIoControlRequest has no hosted device provider and formerly returned successful completion unconditionally; it now rejects absent/unregistered objects and reports unsupported for existing objects rather than inventing data. Guest-thread tests cover counted-name success, missing optical name, invalid pointers, malformed lengths and unchanged device output. These are ABI corrections, not proof of a working optical provider or a complete dashboard. Custom object create/insert callbacks remain a separate task.

The same artifact establishes four distinct custom object creation sites, not one: 816A8B58 (type 81A821E0, 48 bytes), 816BAFC0 (81A82574, 4 bytes), 816F0FB8 (81A85494, r7+24 bytes), and 8188BB04 (81A93738, 4 bytes). All four supply null attributes and a stack output. Each subsequently calls ObInsertObject with zero second/third arguments. The 816F0F78 and 8188BA58 callers explicitly release on insert failure, so a failed insertion must not silently consume the creation pointer reference. A generic implementation needs separate creation and handle insertion, actual descriptor callback dispatch and per-type ownership. A single hardcoded 48-byte allocation is insufficient.

## Verified dispatcher layouts and native custom waits

Run 45955832835 verifies the shared static event words at 81A85484 as 01000000 00000001 81A8548C 81A8548C (type 1, signaled, self-linked wait list). The 48-byte object's constructor at 816A8A54..816A8A78 writes type 1 at body+12, state 0 at +16 and self-linked list at +20/+24. The default-object descriptor field is therefore either an embedded event offset or a high guest-address event pointer for these exact retail types. Single/multiple waits and signal-and-wait now resolve the real dispatcher and hold a pin for its duration. Out-of-range or invalid custom event targets return type mismatch, instead of treating a bodyless host object as immediately signaled. Embedded dispatcher identities are forgotten before pool reuse; shared identities survive custom-object retirement. New guest tests exercise both event shapes, timeout, auto-reset, multiwait and cleanup. Other custom dispatcher types are not inferred. The new tests and retail boot still need execution.

The original fault chain is narrower than a generic callback crash: 819AFF80 selects buffer arguments based on route flags (bytes +5/+6), the input buffer pointer, and two per-logical-CPU pointers at global object 0x81B5B5E4 + dereference +12+8*CPU and +16+8*CPU. The live read at 0x14 therefore proves a zero selected pointer downstream, but does not establish whether the cause is callback wrapping, initialization order, or missing per-processor buffer setup. Added bounded read-only generated probes at 17 original PCs, including registration, original callback, routing entry, virtual dispatch, selected buffer consumption and faulting read. No guest instruction or pointer is changed, and essential PC coverage fails before compiling if unavailable. Tests exercise atomic failure and instrumentation coverage. This is diagnostic evidence, not another speculative fault fix.
