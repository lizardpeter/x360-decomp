# Guest module identity

The pinned SDK's default GetModule resolves built-in kernel modules first. That includes its hosted XAM. With the real retail XAM mapped alongside it, both XexGetModuleHandle and XexLoadImage could return a different instance than the dashboard's verified direct imports. The explicit pre-launch SelectRetailXam API selects the already-mapped, callable retail DLL for guest XAM names only; internal SDK lookups continue to resolve the original hosted service objects. Guest unload cannot consume the selected system module's original load reference. No unknown path is redirected. The preflight now verifies selection rejection, six aliases and unrelated-module isolation against actual loaded modules. This does not yet route imports of additional dynamically loaded XEX modules or prove guest execution; those are separate work.
