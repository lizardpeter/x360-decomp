# XEX backing alias corruption: root cause and correction

Run 45938525434 confirmed six live import failures after repeated-library merging restored ordinal 08E2. The three adjacent slot pairs contain little-endian native pointers, not guest pointers: raw pairs 90368219/a97f0000, 609dee18/a97f0000, 60ce5819/a97f0000. Across runs their high words vary with ASLR. The pinned SDK maps both independently allocated XEX heaps to backing offset 0x80000000. Original XAM has base 0x815f0000 and image size 0x610000, so its native dispatch table begins at 0x81c00000. Its table extends past 0x82000000, aliasing the dashboard loaded at 0x92000000. Table initialization clears dashboard data and registering native function addresses overwrites it. Conversely import relocation overwrites table entries. This accounts for the zeroed slots and the three pointer pairs. It also makes the earlier limited-routing boot's behavior unreliable.

The correction maps the 4 KiB XEX heap to the already available, unused 0x90000000 backing region. The normal guest address arithmetic and existing physical-memory aliases remain intact. This is a hosted native memory isolation correction; it does not model physical page remapping by the retail kernel. The preflight still requires every original binding to resolve; no relaxation. The included SDK regression reproduces the overlap with real allocations and function registration in both directions. The I/O test job's previous failure was a runner path mismatch: the build produced out/linux-amd64/Debug/unit_tests rather than out/build/linux-amd64. Corrected that path and enabled the new regression there as well.

Boot and unit test outcomes are pending.
